# Anvil

**Anvil** is a native Rust AI engineering harness built for **Antigravity**, **Claude Code**, **Cursor**, **Windsurf**, and **Codex**.

Packaged as a single native binary with zero external runtime dependencies, **Anvil** enforces deterministic engineering discipline across AI-assisted workflows: tiered verification, multi-language AST analysis, an incremental code graph, sandboxed **Code Mode**, progressive-disclosure persistent memory, conflict-free team task tracking, and strict token-budget control.

## Overview

Instead of relying on bloated prompt instructions or manual verification habits, **Anvil** keeps `.harness/` as the repository's single source of truth and wires directly into the agent lifecycle through thin adapters, hooks, interactive terminal setup, and a unified MCP server.

- **Multi-language & multi-repo:** supports TypeScript/JavaScript, React, Vue/Svelte SFC, Angular, NestJS, Next.js, Astro, Vite, Python, Kotlin/Android, Flutter/Dart, Rust, PHP 8.x / Laravel (API, Blade, Inertia, and Livewire), and **Godot 4** (GDScript, `.tscn`, `.gdshader`) across single repositories, monorepos, and thin-umbrella multi-repo workspaces.
- **Token-efficient & Code Mode enabled:** inspects symbol outlines and exact AST slices before reading full files, runs chained read-only queries inside a pure-Rust JS sandbox (`code_exec` / `anvil code exec`), wraps external MCPs behind `anvil mcp --proxy`, guards against reading lockfiles/bundles whole, and compresses compiler/test output into bounded summaries.
- **Evidence-first verification:** combines deterministic AST checks, anti-test-tampering diff guards, reverse blast-radius analysis, architecture boundary/cycle rules, opt-in local **SonarQube** integration, and scoped execution of native typecheckers and test runners.

## Harness Layers (11 Crates)

### 1. Core & Operational Control (`anvil-core`)
Manages repository configuration (`.harness/config.json`), `.gitignore`-aware stack and tool detection, semantic diff classification (`docs`, `style`, `config`, `logic`, `contracts`, `UI`, `deps`), token-bounded output compression, content-addressed Tier 1 check caching (`blake3`), anti-test-tampering diff analysis (`no-test-tampering`), opt-in local **SonarQube** Web API & complexity checks, an always-on Tier 0 check that rejects added lines duplicating existing code (`anvil-allow(duplication): <reason>`), trajectory telemetry (`anvil stats --trajectories`), the **`N=3` Circuit Breaker** against blind retries, and the **Ratchet** engine for graduating recurring mistakes into deterministic rules (`--severity error|warn|info`, automatic `fp_checked` verification in `anvil ratchet test`, and human-approved promotion).

### 2. AST & Tier 0 Rules (`anvil-ast`)
Embeds `tree-sitter` grammars in a single-pass parser pool (plus dedicated Vue/Svelte SFC and Godot 4 `.gd`/`.tscn`/`.gdshader` parsers) to extract symbols, line spans, call/import edges, HTTP routes, and template references while running sub-second deterministic Tier 0 checks: blocking unapproved escape hatches, deferred/narrative comments, strict-type violations (`any`, `dynamic`, `declare(strict_types=1)`), PHP/Laravel & Godot hygiene issues, swallowed errors in newly added code (empty `catch`, `.catch(() => {})`, `except: pass`, `Err(_) => {}`), pure barrel re-exports, root hygiene violations, and unverified permission assumptions.

### 3. Code Graph & Tier 1 Impact (`anvil-graph`)
Maintains a parallel, incremental binary code graph (`postcard`) with native resolution across TSConfig, Angular, NestJS, Python, Kotlin/Gradle, Dart, Rust/Cargo, PHP PSR-4, Blade/Inertia/Livewire, Godot scenes/autoloads, and cross-stack HTTP routes. Powers reverse-BFS blast radius, upstream origin tracing, architecture boundary & circular-import checks, signature-only outlines, targeted symbol reads, and scoped Tier 1 typecheck and test execution (including native `node --test` alongside `vitest`/`jest` and language-native runners).

### 4. Persistent Memory (`anvil-memory`)
Combines local SQLite FTS5 indexing with Git-friendly JSONL chunks (`.harness/memory/chunks/`) using progressive disclosure (*search → timeline → get*), automatic secret redaction, and staleness detection tied to the live code graph.

### 5. Sandboxed Code Mode (`anvil-codemode`)
Embeds a pure-Rust JavaScript engine (`boa_engine`) enabling agents and CLI users to batch, filter, and transform multiple read-only Anvil MCP calls in a single round-trip (`code_exec`, `anvil code exec`), or compress external stdio MCP servers via `anvil mcp --proxy` (`proxy_search` + `proxy_exec` with mutation guards and secret redaction).

### 6. Tier 2 Verification (`anvil-deps` & `anvil-qa`)
- **Dependency Auditing (`anvil-deps`):** audits npm, PyPI, pub.dev, Maven, Cargo, and Composer/Packagist manifests for deprecated, abandoned, >24-month stale packages, and **OSV.dev** vulnerabilities with TTL caching.
- **Hybrid Visual QA (`anvil-qa`):** pairs programmatic Web DOM and Mobile view-tree checks (Playwright, Chrome DevTools, ADB/`uiautomator`, `logcat`, Roborazzi, and headless Godot GUT/render QA) with before/after visual verification.

### 7. Conflict-Free Task Ledger & Feature Lists (`anvil-tasks`)
Tracks tasks with short sequential codes (`T-001`, `T-002`, ...) or 1-level grouped directories (`.harness/tasks/<group>/<ID>/` via `--group`/`--flat` or `--id F039`), immutable per-author ULID entries, and crash-safe per-task `progress.md` checkpoints. Root `tasks.json` is kept as a compact v2 index pointing to `.harness/tasks/<ID>/progress.md` (without duplicating `entries` or `files_touched`), backed by a Git merge driver (`anvil tasks merge-driver`) — teams wanting zero root PR churn can optionally add `tasks.json` to `.gitignore` with zero runtime impact. Also supports strictly single-task execution and interruption recovery (`anvil tasks start|update|done|resume`, `SessionStart` Resume Briefs), decomposing monolithic `feature_list.json` requirement lists (`anvil tasks import` with native OS / arrow-key TUI file browser), verifying `verify` commands (`anvil tasks verify --record`), exporting snapshots (`anvil tasks export`), migrating legacy IDs (`anvil tasks migrate-ids`), and full MCP lifecycle tools (`task_start`, `task_update`, `task_done`, `task_resume`, `task_list`, `task_get`).

### 8. Adapters, MCP Server & CLI (`anvil-adapters`, `anvil-mcp`, `anvil-cli`)
- **Thin Adapters (`anvil-adapters`):** translate lifecycle hooks (`SessionStart`, `PreInvocation`, `PreToolUse`, `PostToolUse`, `Stop`), **Security Guard**, **Token Guard**, **Availability Guard** (gracefully skips `anvil:managed` blocks when `anvil` is absent from `PATH`), and synced configs/rules for Antigravity, Claude Code, Cursor, Windsurf, and Codex (including thin-umbrella multi-repo routing).
- **Unified MCP Server (`anvil-mcp`):** exposes 27 code-graph, search, memory, task, review, and Code Mode tools over `stdio` JSON-RPC 2.0, plus `--proxy` gateway mode.
- **CLI & Daemon (`anvil-cli`):** provides interactive arrow-key Clack-style TUI initialization (`anvil init`), Git ref snapshots (`anvil checkpoint`), isolated agent worktrees (`anvil worktree`), spec contracts (`anvil spec`), opt-in SonarQube commands (`anvil sonar`), a Claude Code orchestrator/executor model pair (`anvil orchestrator`), diagnostics (`anvil doctor`), machine prerequisites (`anvil prereqs`, crate `anvil-prereqs`), and an optional resident TCP daemon.

## Install

From source (needs a Rust toolchain; builds the release binary and copies it to `~/.cargo/bin`, or `~/.local/bin` when that does not exist):

```bash
scripts/install.sh                 # Linux and macOS
cargo install --path crates/anvil-cli   # alternative on any platform
```

```powershell
scripts/install.ps1                # Windows: installs to ~\.cargo\bin or %LOCALAPPDATA%\anvil\bin
```

From a GitHub release (no Rust toolchain needed; verifies the published SHA-256 checksum before installing):

```bash
scripts/install.sh --from-release                      # latest release
scripts/install.sh --from-release --version v0.1.0     # a specific tag
```

```powershell
scripts/install.ps1 -FromRelease                       # latest release
scripts/install.ps1 -FromRelease -Version v0.1.0       # a specific tag
```

Both release modes use `gh release download`, so run `gh auth login` first while the repository is private. `install.sh` falls back to `curl` when `gh` is missing, which only works for public repositories. Set `ANVIL_REPO=owner/name` to install from a fork, and use `--install-dir` / `-InstallDir` to change the destination.

On Windows the installer stops the daemon and renames a running `anvil.exe` to `anvil.exe.old` before copying the new one. An `anvil mcp` server that is already running keeps the old version until its client restarts it.

Release targets (archives are named `anvil-<tag>-<target>.zip` on Windows and `.tar.gz` elsewhere, each with a `.sha256` file):

| Platform | Targets |
|----------|---------|
| Windows | `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc` |
| Linux | `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl` (static, used by `install.sh`), `aarch64-unknown-linux-gnu` |
| macOS | `aarch64-apple-darwin`, `x86_64-apple-darwin` |

Pushing a `v*` tag publishes the release. Running the workflow manually (`workflow_dispatch`) builds every target as a dry run and keeps the archives as workflow artifacts only.

## Quick Start

```bash
# Interactive setup (single repo, monorepo, or thin-umbrella multi-repo + opt-in SonarQube)
anvil init

# Verify changes (Tier 0 AST + Tier 1 blast-radius/typecheck/tests + Tier 2 QA/deps)
anvil check

# Crash-safe task lifecycle & feature_list.json import
anvil tasks import
anvil tasks start <ID|title>
anvil tasks resume

# Query the codebase in one sandboxed JS call via Code Mode
anvil code exec "return anvil.graph_query({ term: 'init', limit: 5 });"

# Claude Code: pair a planning model with a cheaper execution model (model + effort each)
anvil orchestrator setup
anvil orchestrator on               # enforce roles: the orchestrator judges, executors write within SCOPE
anvil orchestrator tools            # choose which of your MCP servers executors load (or --add postgres,chrome-devtools)

# Executor model and effort selector above the Claude Code prompt (the orchestrator uses the native picker)
anvil plugin install

# Record problems review finds after `anvil check` was green; `anvil stats` reports the escape rate per category
anvil review log "unchecked input" --category error-handling --severity high --file src/a.rs:10
anvil review list --since 7

# Optional local SonarQube status & repo health check
anvil sonar status
anvil doctor
```

## Prerequisites

`anvil prereqs` answers "does this machine have everything the project needs?" from the files the project already has, so a hand-written `init.sh` can no longer drift from `engines.node`, `requires-python` or the Gradle daemon JVM.

```bash
anvil prereqs detect [--write]     # what the project files ask for; --write stores it in .harness/config.json
anvil prereqs check [--json] [--subrepo NAME]   # table of checks; exit 1 when a required item fails
anvil prereqs script [--out DIR]   # writes init.sh and init.ps1, thin wrappers around the check
anvil doctor --prereqs             # the same check inside doctor (plain doctor shows a one-line summary)
```

`anvil init` stores the detection in the `prerequisites` section of `.harness/config.json`; `detect --write` refreshes it. Per repo and per subrepo it reads `package.json` (`engines`, `packageManager`, `volta`), `.nvmrc`, `.node-version`, `.tool-versions`, `mise.toml`, lockfiles, `.npmrc` (`legacy-peer-deps`), `pyproject.toml` (`requires-python`, uv, Poetry, `.venv`), `Cargo.toml` (`rust-version`), `go.mod`, Gradle (`gradle-daemon-jvm.properties`, `jvmToolchain`; `JAVA_HOME` must match), Android and iOS markers (SDK, `adb`, Xcode and CocoaPods on macOS only), `pubspec.yaml`, `composer.json`, Terraform (`required_version` and the CI `terraform_version` pin; inside WSL on Windows), Docker Compose (with the DB clients behind it), `sonar-project.properties` (`sonar-scanner` and its env names), `.github/` (`gh`), Karma, Playwright and `.mcp.json` (Chrome), and always `git` and `anvil`.

A check reports `ok`, `missing`, `wrong_version` or `warning` per item, with the version found, the constraint, where it came from and an install hint. Besides tools it checks:

- **Env files:** every key of `.env.example` must exist in `.env` (BOM and CRLF tolerated). Only key names are ever printed, never values.
- **MCP servers in `.mcp.json`:** the command resolves on `PATH` (or the absolute path exists); a path inside another user's profile is flagged; archived packages such as `@modelcontextprotocol/server-postgres` (archived 2025-05, unpatched) and `server-github` are flagged with a replacement; inline credentials in args or env are flagged by scheme and host only.
- **Secret hygiene scan (warnings):** `scheme://user:password@host` connection strings in `.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `.claude/settings*.json`, `.agents/*.json`, `.mimocode/*.json` and files under `scripts/` and `harness/` (up to 512 KB). Output is `file:line` and `scheme://host`; the password is never printed.

Only required items that are missing or outdated make `check` exit 1; warnings never do. Overrides live next to the detected set and survive `detect --write`:

```json
{ "prerequisites": {
    "extra_tools": [{ "name": "psql", "version": ">=16", "required": false, "hint": "brew install libpq" }],
    "ignore": ["gh"],
    "custom": [{ "name": "db reachable", "command": "pg_isready -h localhost", "hint": "docker compose up -d" }]
} }
```

Custom checks run through the shell under a timeout; exit 0 means ok. In a monorepo every entry carries its `subrepo`, so one flat list in `prerequisites` covers all of them.

`anvil prereqs script` writes `init.sh` and `init.ps1` to the repository root and adds them (and `init.cmd`) to the root-hygiene allowlist. They check that `anvil` is on `PATH` (otherwise they print the install commands from the Install section above), run `anvil prereqs check "$@"` and exit with its code, so `./init.sh --json` and `.\init.ps1 --subrepo api` work.

## Architecture Presets

`anvil init` can record which architecture a project follows. Each style is a preset that is (a) expanded into import rules `anvil check` verifies and (b) stated to the agents. The rules are generated when checks run; they are never written into `boundaries`, which stay yours.

```bash
anvil architecture detect                       # suggest a style from the folder names (changes nothing)
anvil architecture set hexagonal [--subrepo NAME] [--source-root DIR]
anvil architecture show [--json]                # style per repo/subrepo, generated rules, agent guidance
anvil architecture check [--json]               # the whole repo, not just the diff; exit 1 on a violation
anvil init --architecture hexagonal             # or: auto (default), none, clean, layered, feature-sliced, modular-monolith, event-driven
anvil sync                                      # writes one Architecture line per style into CLAUDE.md, AGENTS.md, Codex, Cursor, Windsurf
```

`check` prints `file:line -> target`, the rule name and the reason that teaches the fix. `anvil check` (Tier 1) applies the same rules to the changed files, and SessionStart gives the agent the same `Architecture:` line. In orchestrator mode `show`, `detect` and `check` are readable by both roles; `set` is a writer (executors only).

```json
{ "architecture": {
    "style": "hexagonal", "source_root": "src", "modules": ["orders", "customers"], "strict_framework": false,
    "subrepos": { "orders-api": { "style": "hexagonal" }, "web": { "style": "feature-sliced" } }
} }
```

`style` is `none` (default), `hexagonal`, `clean`, `layered`, `feature-sliced`, `modular-monolith` or `event-driven`. `source_root` (default `src`) anchors every rule; under a subrepo it is relative to the subrepo path. `modules` limits module isolation to those directories (default: every directory under the source root, or under `<source_root>/modules` when that exists). `strict_framework` (hexagonal) also forbids `@nestjs/*` in `application/`. Per-subrepo choices live in `architecture.subrepos`, keyed by subrepo name, so stack detection (which rebuilds `subrepos`) never wipes them. Generated rule names start with `arch:<style>:` (subrepo rules end in `@<subrepo>`) and show up as `boundary:arch:...` in `anvil check`.

| Style | What is enforced |
| --- | --- |
| `hexagonal` | `domain/` imports no `application/`, no infrastructure folder (`infrastructure`, `infraestructure`, `infra`, `adapters`, `persistence`) and no delivery folder (`controller(s)`, `presentation`, `api`, `http`, `web`, `graphql`). `application/` imports no infrastructure or delivery. Infrastructure imports no delivery. `domain/` imports no `@nestjs/*`, `typeorm`, `@prisma/*`, `mongoose`, `sequelize`, `express`, `fastify`, `class-validator`, `class-transformer`, `axios`, `pg`, `mysql2`, `redis`, `ioredis`. `application/` imports no `typeorm`, `@prisma/*`, `mongoose`, `sequelize`, `express`, `fastify`, `axios`, `pg` (`@nestjs/common` stays allowed for `@Injectable`/`@Inject`). A module reaches another only through its `domain/`, `application/`, `*.module.*` or `index.*` (shared kernels such as `shared/` and `common/` are exempt, as under `modular-monolith`). |
| `clean` | Rings `entities\|domain` <- `use-cases\|usecases\|application` <- `adapters\|interface-adapters\|controllers\|presenters\|gateways` <- `frameworks\|infrastructure\|drivers\|main`; an inner ring never imports an outer one. |
| `layered` | `repository\|repositories\|dao\|models` import no `service(s)`, `controller(s)` or `routes`; `service(s)` import no `controller(s)` or `routes`. |
| `feature-sliced` | `app > processes > pages > widgets > features > entities > shared`: a layer never imports a higher one, and slices of one layer (`features/a`, `features/b`) never import each other. |
| `modular-monolith` | Modules (`<source_root>/modules/*`, else `<source_root>/*`) import each other only through `index.*`, `*.module.*`, `public/**` or `api/**`. `shared`, `common`, `core`, `config`, `utils`, `lib(s)` and `kernel` are shared kernels: they may be imported freely and are not themselves checked (they hold app-wide wiring such as the database config). |
| `event-driven` | Files in `handlers/`, `consumers/` and `subscribers/` do not import another context's internals (only its public API or `events/`, `contracts/`, `*.event.*`). The guidance matters most here: publish and consume through the event bus, keep handlers idempotent, never call another context directly. |

How the rules are checked: besides resolved file imports, generated rules look at imports the graph could not resolve to a file (packages). The package name is taken from the specifier (`typeorm/repository` is `typeorm`, `@nestjs/common/decorators` is `@nestjs/common`); relative and alias paths (`./x`, `@/x`, `~/x`) are never packages. Package rules apply to TypeScript, JavaScript, Vue and Svelte files. Spec and test files (`*.spec.*`, `*.test.*`, `__tests__/`, `test/`, `tests/`, `e2e/`) are not held to the rules, and files outside any module (such as `src/app.module.ts`, the composition root) may import anything. User `boundaries` keep their own glob semantics (`*` within a segment, `**` across segments) unchanged.

`anvil init --architecture auto` detects a style from the folders under the source root (most modules with `domain` + `application` + an infrastructure folder: hexagonal; `entities` + `use-cases`: clean; `features` + `entities` + `shared`: feature-sliced; `controllers` + `services` + `repositories`: layered) and prints it with a confidence note. In an interactive terminal `anvil init` always asks, even in an empty folder: you pick one of the presets or `none` from a select prompt that defaults to the detected style, else `none` (per subrepo in a monorepo), and for an empty project the rules apply once code exists under `src`; without a prompt it only suggests, because enforcing a guessed style could fail builds unexpectedly.

## Code Search

`anvil grep <pattern> [paths]...` and the MCP `grep` tool search the repository with ripgrep's own crates (`ignore`, `grep-regex`, `grep-searcher`). Nested `.gitignore` and `.ignore` files, negations, and global git excludes are honoured, binaries and files over 512 KB are skipped, and hidden files are skipped unless `--hidden` is passed (`.github/`, `.claude/`, and `.agents/` are always searched, and so are `.harness/docs/`, `.harness/rules/`, `.harness/skills/`, and `.harness/config.json`; the `.harness/` ledgers `tasks/`, `memory/`, and `candidates/` and the runtime `.state/` and `.worktrees/` are never searched). Lockfiles, minified bundles, and generated directories stay out, as in the other Anvil commands.

Results are grouped by file in a token budget (`--max-tokens`, `--max-matches`, `--max-per-file`), and the footer reports the exact totals even when the listing is cut. When a code graph exists (`anvil graph build`), every match shows its enclosing symbol, for example `42: return find_user(id)  [fn handle_request]`. Flags: `-i`, `-s/--case-sensitive` (smart case is the default), `-F`, `-w`, `-g <glob>` (repeatable), `-C <n>`, `-l`, `--hidden`, `--json`, `--backend`. Exit status is 0 with matches, 1 without, and 2 on error.

The engine is chosen with `search.backend` in `.harness/config.json` (`--backend` overrides it per call):

```json
{ "search": { "backend": "auto" } }
```

- `builtin`: the engine described above.
- `tgrep`: use [Microsoft tgrep](https://github.com/microsoft/tgrep) (trigram index, ripgrep-compatible `--json`). Anvil applies its own noise filter, caps, and budget to the results. When `tgrep` is missing or fails, the built-in engine answers and the report carries a note.
- `auto` (default): use `tgrep` only when it is on `PATH`, `<repo>/.tgrep/` exists, and `tgrep status` reports a running server with an active file watcher for the repository, so results are fresh. Otherwise the built-in engine runs.

Anvil never builds a `.tgrep/` index or starts `tgrep serve`; run `tgrep serve` yourself on large repositories to get indexed search. Without a running server, `tgrep` results can lag file changes. Both backends apply the same hidden-file rules.

## Search Cascade

Every lookup follows one order: **code graph -> living docs -> code**. Reading a symbol from the graph or a concept from `.harness/docs/` costs a fraction of grepping files, so grep comes last.

- `anvil search <query> [--code] [--limit N] [--max-tokens N] [--json]` and the MCP tool `search` ("Start here: looks the query up in the code graph, then the living docs, then the code (grep) only if needed.") run the cascade and print one block per stage: up to 8 graph hits (symbol or file, `file:line`), up to 5 docs hits (concept id, path, snippet), and grouped code matches with their enclosing symbols. The header names the stage that answered and the last line suggests the next step (`graph_read_symbol <id>`, `Read .harness/docs/...`, or a narrower `grep`).
- The code stage runs only when graph and docs together return fewer than 3 hits, when `--code` / `"code": true` forces it, or when the query is clearly literal text (quoted, or containing punctuation such as `(`, `=`, or `\` that symbol search cannot match). The three sections share one token budget (`--max-tokens`, default 1200). A missing graph or docs bundle is a one-line note in its section, never an error; the cascade never builds a graph.
- The MCP server states the order in the `instructions` it returns on `initialize`.

**Once per turn.** The `PreToolUse` hook answers the first code search of each turn, per agent (the main thread and every subagent count separately), with a denial that quotes the graph and docs results for the searched pattern (about 600 tokens) and says "Graph and docs were checked first; repeat the search if you still need the code." The repeat goes through. Code searches are the `Grep`, `Glob`, `grep_search`, and `find_by_name` tools, the MCP `grep` tool, and `rg`, `grep`, `egrep`, `fgrep`, `findstr`, `Select-String`, `ag`, `ack`, `git grep`, `tgrep`, or `anvil grep` in the shell, when they search inside the repository (piped filters such as `cmd | grep x` and searches of paths outside the repository are never blocked). A turn counts as consulted as soon as the agent used `search`, a `graph_*` tool, `context_pack`, or `code_exec`, read a file under `.harness/docs/`, or ran `anvil search|graph|docs search|context`; a new user prompt clears the flags. Nothing happens when there is neither a graph nor a docs bundle, or when graph and docs have no hit for the pattern.

`search.cascade` in `.harness/config.json` sets the behaviour:

```json
{ "search": { "cascade": "enforce" } }
```

- `enforce` (default): deny the first code search of the turn as described above.
- `advise`: never block; queue a one-line advisory with the top graph or docs hit, delivered with the next tool result.
- `off`: do not interfere with code searches.

## Living Docs (OKF)

`anvil docs` keeps project documentation next to the code as an [Open Knowledge Format](https://github.com/open-knowledge-format/open-knowledge-format) (v0.3) bundle: Markdown concepts with YAML frontmatter under `.harness/docs/<project>/` (one bundle per project; a monorepo gets one per `subrepos` entry, a single repository uses `docs.project` or its folder name). `index.md` lists the modules and `log.md` is the dated history; both are reserved. Files without a `type` (such as `PLAN.md`) are left alone.

```bash
anvil docs init                                   # create index.md and log.md (idempotent)
anvil docs new orders --paths "src/orders/**"     # <module>/overview.md with Purpose, Responsibilities, Public interface, Invariants, Dependencies, Related
anvil docs scaffold [--depth N]                   # a concept for every module without one, from the code graph (anvil graph build first)
anvil docs list [--json]                          # status, trust tier, stale flag and reason
anvil docs check [--strict] [--json]              # validation errors exit 1; stale concepts exit 1 only with --strict
anvil docs refresh <id>... | --stale              # after updating a doc: regenerate the outline, restamp generated and the synced commit, log it
anvil docs verify <id> [--by <name>]              # a human review; agents never run it
anvil docs search <query> [--limit N] [--json]    # BM25 over title, description, tags, headings, and body
```

Concepts carry two Anvil extensions: `x-anvil-paths` (repo-relative globs of the documented code) and `x-anvil-synced-commit` (the commit the doc was synced to; `x-anvil-synced-digest` fingerprints uncommitted changes present at sync time so a refresh is not stale until the code changes again). A concept is **stale** when a file matching its globs changed since that commit (committed, uncommitted, or untracked) or when the commit is unknown. The trust tier is `unverified`, `machine-confirmed`, or `human-reviewed`; a `human:` verification only counts when it is at or after `generated.at`. The block between `<!-- anvil:outline:start -->` and `<!-- anvil:outline:end -->` in "Public interface" is generated from the graph; all other text is preserved byte for byte.

Hooks keep it current: after an agent edits a file a concept documents, it gets one reminder per concept per turn; edits of a concept are validated; `Stop` lists concepts whose code changed but which were not refreshed; and `anvil check` reports invalid changed docs as Tier 0 errors and stale concepts as warnings. `anvil docs verify` always asks the user and is refused in orchestrator mode. Config (`.harness/config.json`): `"docs": { "project": "name", "remind_on_edit": true }`.

## Prompt Assist

Rough requests get worse results. Anvil helps without calling a model or the network: everything below is deterministic and comes from the repository's own graph, docs, memory, and config.

**What every prompt gets.** The `UserPromptSubmit` hook (and Antigravity's `PreInvocation`) adds one short line for the agent so it starts in the right place:

```
[info][prompt-context]: Likely relevant (verify before relying): code: applyDiscount (src/orders/order.ts:7); docs: shop/orders — Orders [stale]; memory: Totals use integer cents (decision).
```

Code symbols come from identifiers in the prompt (`camelCase`, `snake_case`, `kebab-case`, `a.b.c`, paths like `src/x.ts`, backticked or quoted names) that resolve in the graph, plus symbols whose own name shares two words with the prompt; docs concepts and memories need two words in common as well. English and Spanish filler words are ignored. Nothing relevant means no line at all. The whole block is capped at `max_tokens` (default 450, estimated at 4 characters per token); an item shown in the last 3 prompts of the same session is not repeated. Slash commands, injected text starting with `<`, prompts shorter than `min_words` (default 4), and repositories without `.harness/` are skipped. Gathering has a 250 ms budget and never runs a text search; the code graph is read from disk, never built.

**Off by default, and global.** Prompt assist does nothing until you turn it on. It is a setting of the person, not of a repository: it lives in `~/.anvil/config.json` (`%USERPROFILE%\.anvil\config.json` on Windows, next to `.cargo`), is shared by every project, and is never written to `.harness/config.json`. `ANVIL_HOME` replaces the whole `.anvil` directory. Turn it on with `anvil prompt assist context` or `anvil prompt assist coach`, off again with `anvil prompt assist off`; `anvil prompt assist` alone shows the current mode and the file path. `--max-tokens N` and `--min-words N` set the other two values. An unreadable or invalid file is logged in `.harness/.state/hook-errors.log` and treated as off. `anvil prompt improve` always works, whatever the mode.

**Modes** (`anvil prompt assist [off|context|coach]`; `off` is the default and is not written to the file):

| Mode | What is added |
| --- | --- |
| `off` | Nothing. |
| `context` | The line above. |
| `coach` | The line above, plus, when the request has no target, no statement of the expected result, or a very broad scope ("everything", "toda la app"), a `prompt-coach` note for the agent: restate the goal, propose acceptance criteria and how to verify them (`anvil check`, `anvil qa api` and `anvil qa run --all-flows` when scenarios and flows exist), and ask the user to confirm before editing. The user sees one short tip (Claude Code `systemMessage`), at most once per session per kind of gap. |

```json
{ "prompt_assist": { "mode": "coach", "max_tokens": 450, "min_words": 4 } }
```

**Improve a request.** `anvil prompt improve "<text>"` (or `-` / no argument to read stdin; `--json` for structured output) prints the request as a prompt you can review and edit. Sections are built from the repo: the goal unchanged, the symbols, docs, and memories found (with a text search for the words the graph cannot name), the architecture guidance, the escape-hatch rule and the security guard, acceptance criteria (a checklist with derived items and `<describe ...>` placeholders), the verification commands this repo really has, and open questions for each gap.

```
$ anvil prompt improve "add a discount when quantity is over 10"
## Goal
add a discount when quantity is over 10

## Context
- code: `Order` (class orders-api/src/orders/domain/order.ts:28)

## Constraints
- Architecture: hexagonal (ports & adapters) in this repository: domain imports no framework or other layer; ...
- Do not add suppressions or escape hatches (...); if one is truly needed, justify it as `anvil-allow(<rule>): <reason>`.

## Acceptance criteria
- [ ] `anvil check` passes (lint, types, architecture rules)
- [ ] API scenarios pass: `anvil qa api`
- [ ] <describe what done looks like>

## Verification
- `anvil check`: lint, types, architecture rules, and the tests related to the changed files
- `anvil qa api`: 3 API scenario(s): create-and-pay-order, invalid-quantity, unknown-customer
- `anvil qa run --flow create-order`

## Open questions
- What should be true when this is done (expected result, error cases)?
```

The built-in `improve-prompt` skill tells the agent to run it when a request is vague, show the result, and wait for the user's confirmation before editing. In orchestrator mode `anvil prompt improve` is read-only; `anvil prompt assist` with a mode or flag is not (it writes your global config).

## Web QA

Agents should verify web changes in a running browser, not by reading the code. Anvil offers two complementary ways.

**Repeatable flows (`anvil qa`).** A flow is a JSON file in `.harness/qa/flows/` (`qa.web.flows_dir`). `anvil qa run --flow <name>` or `--all-flows` runs it in headless Chromium through Playwright, records every request (method, URL, status, resource type, duration) plus console and page errors, judges the expectations in order, and exits 1 on any failed expectation, page error, console error, or visual diff.

```json
{ "name": "create order", "url": "/", "viewport": "desktop",
  "steps": [
    { "goto": "/" },
    { "wait_for": "table tbody tr" },
    { "fill": { "selector": "#item", "value": "Widget" } },
    { "select": { "selector": "#customer", "index": 1 } },
    { "click": "button[type=submit]" },
    { "expect_request": { "method": "POST", "url_contains": "/orders", "status": 201 } },
    { "expect_text": "Widget" },
    { "expect_visible": "table tbody tr" },
    { "screenshot": "after-create" }
  ] }
```

Steps: `goto`, `wait_for`, `fill {selector, value}`, `select {selector, index | value}`, `click`, `press` (`"Enter"` or `{selector, key}`), `wait_ms` (capped at 10 s), and the expectations `expect_request {method?, url_contains, status?}`, `expect_no_request {url_contains}`, `expect_text`, `expect_visible`, `expect_count {selector, count}`, and `screenshot` (a name, or `{name, selector?, mask?, full_page?}` to capture one element and mask dynamic parts). Selectors are Playwright selectors (CSS, `text=`, `role=`). Relative URLs resolve against `qa.web.url`; `viewport` is `desktop` (1440x900) or `mobile` (390x844); `timeout_ms` changes the per-step timeout (default 10 s). Request expectations look at the traffic since the last `goto`, `click`, or `press` step, and wait for it up to the timeout. A "Failed to load resource" console error caused by a request a passing `expect_request` expects to fail (status 4xx/5xx) does not count as a console error. Unknown steps or keys are rejected with the list of valid ones; `anvil qa flows` lists and validates every file. Playwright is found in the repository or in any app folder one or two levels below it (or `qa.web.start_cwd`).

`anvil qa run [URL]` without `--flow`/`--all-flows` keeps the DOM audit. `--start` runs `qa.web.start_command` in `qa.web.start_cwd`, waits until `url + ready_path` answers, runs, and stops the whole process tree (an app that already answers is left alone). `--json` prints the structured report: step results with the requests each `expect_request` matched, the network log, errors, and screenshot paths under `.harness/.state/qa/<run-id>/`.

**Visual baselines.** `anvil qa baseline [--flow NAME]` runs the flows and stores their `screenshot` steps in `.harness/qa/baseline/<flow>/<name>.png` (only for flows that otherwise passed). Later runs compare each screenshot with its baseline: a pixel counts as changed when a channel differs by more than 8/255, the run fails when the share of changed pixels exceeds `qa.web.diff_threshold` (default `0.01`), a diff PNG is written next to the new screenshot, and a size change fails with both sizes. Screenshots without a baseline only produce a note.

```json
"qa": { "web": {
  "url": "http://localhost:5173", "start_command": "npm run dev", "start_cwd": "web",
  "ready_path": "/", "ready_timeout_secs": 60,
  "flows_dir": ".harness/qa/flows", "diff_threshold": 0.01, "autostart": false } }
```

**Tier 2.** When a diff touches UI files and `qa.web.url` is set, `anvil check` probes the URL (2 s). If it answers (or `autostart` is true and `start_command` is set, in which case Anvil starts and stops the app) it runs every flow, or the DOM audit when there are none, and fails Tier 2 on failures with a compact per-flow summary: the failed step and reason, unexpected 4xx/5xx responses, console errors, and visual diff ratios. If the app is not reachable it prints an advisory with the start command and does not fail. The driver `skip` disables it.

**Chrome DevTools MCP.** `anvil qa select-web chrome_dev_tools` (and every `anvil sync` afterwards) registers Google's `chrome-devtools-mcp` as the `chrome-devtools` server in each adapter's MCP config (`.mcp.json`, `.agents/mcp_config.json`, Cursor, Windsurf, Codex) and adds `mcp__chrome-devtools__*` to `orchestrator.executor_tools` when an orchestrator is configured. The command is `npx -y chrome-devtools-mcp@1.14.0 --isolated --headless --no-usage-statistics --no-performance-crux` (`cmd /c npx ...` on Windows, where `npx` is a `.cmd` shim); the version is pinned in `anvil_adapters::web_qa::CHROME_DEVTOOLS_MCP_VERSION`. The flags matter for privacy: the server sends usage statistics to Google unless `--no-usage-statistics` is given, and performance traces look up the visited URLs in the Chrome UX Report unless `--no-performance-crux` is given, which must be off for local apps. `--isolated` uses a temporary browser profile. Changing the driver to anything else removes the entry again; an entry named `chrome-devtools` that Anvil did not write (different arguments) is never changed or removed. The `visual-qa` skill tells agents to use the tools for interactive checks (`take_snapshot` before screenshots, `list_console_messages`, `list_network_requests` to confirm the expected calls, a performance trace for Core Web Vitals) and flows for repeatable ones.

## API QA and database checks

An agent that changes a backend should prove the change works: call the running API, then look in the database. A scenario is a JSON file in `.harness/qa/api/` (`qa.api.scenarios_dir`) whose steps make HTTP calls and run read-only database queries through [Google MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) (`toolbox invoke`). The same Toolbox file can be registered as an MCP server so agents query the database themselves.

**Configuration** (`.harness/config.json`; defaults are left out of the saved file):

```json
"qa": { "api": {
  "url": "http://localhost:3100", "start_command": "npm start", "start_cwd": "orders-api",
  "ready_path": "/health", "ready_timeout_secs": 60,
  "scenarios_dir": ".harness/qa/api", "autostart": false, "paths": ["orders-api"] } },
"db": { "toolbox": ".tools/toolbox.exe", "config": ".harness/db/tools.yaml", "mcp": false }
```

`qa.api.paths` are the path prefixes whose changes trigger the Tier 2 step (`start_cwd` when empty). `db.toolbox` is a name on `PATH` (default `toolbox`) or a path relative to the repository root. Toolbox always runs from the repository root, so a SQLite `database:` path inside the tools file is written relative to the root (that is also the directory MCP clients start servers in).

**Set up the database.** `anvil db init --kind sqlite|postgres|mysql [--database <file|name>] [--name app-db] [--toolbox <binary>] [--force]` writes `.harness/db/tools.yaml`: one source plus the managed `anvil_select` tool (`sqlite-execute-sql`, `postgres-execute-sql`, or `mysql-execute-sql`, which takes one `sql` parameter) and saves the `db` section. For SQLite without `--database` it reads only the `DB_PATH`-style variables (`DB_PATH`, `DATABASE_PATH`, `SQLITE_PATH`, `DATABASE_URL=sqlite:...`) of the `.env*` files of the root and its direct subfolders; no other value is read or printed. Server databases get `${DB_HOST}`, `${DB_PORT}`, `${DB_USER}`, `${DB_PASSWORD}`, `${DB_NAME}` placeholders: Toolbox substitutes environment variables itself, so credentials never go into the file (`--database` names the database literally instead of `${DB_NAME}`). It refuses to overwrite an existing file without `--force`. Install the Toolbox binary from the [releases page](https://github.com/googleapis/mcp-toolbox/releases) (v1.18.0 is what Anvil was verified with).

- `anvil db check` reports the Toolbox binary and version, the tools file, every credential-like key (`password`, `secret`, `token`, ...) whose value is not a `${VAR}` placeholder (the value is never printed), and runs `SELECT 1` through `anvil_select`. Exit 1 on any failure. `anvil doctor` shows the binary when `db` is configured.
- `anvil db query "SELECT ..."` prints the rows as JSON.
- `anvil db mcp on|off` registers or removes the `anvil-db` MCP server (`<toolbox> --stdio --config <db.config>`) in `.mcp.json`, `.agents/mcp_config.json`, Cursor, Windsurf, and Codex, and grants `mcp__anvil-db__*` to executors when an orchestrator is configured. `anvil sync` keeps it in line with `db.mcp`. An `anvil-db` entry Anvil did not write (different arguments) is never changed or removed. The MCP server can run any statement its tools allow, and calls with a `sql` field already go through the security guard (destructive SQL asks); use a read-only database user for anything beyond local development.

**Read-only rule.** `db.sql` steps, `anvil db query`, and the `anvil_select` tool when named in a scenario only run one `SELECT` or `WITH ... SELECT`: anything else (another first keyword, a second statement after `;`, or a write keyword such as `INSERT`, `UPDATE`, `DELETE`, `DROP`, `INTO`, `PRAGMA` outside string literals and comments) is refused as a step error before Toolbox is called. This is a guard against mistakes, not a permission system; the real defense is a database user that can only read.

**Scenario format.** A step has exactly one of `http` or `db`, plus an optional `name`, `expect`, and `capture`:

```json
{ "name": "create and pay order",
  "vars": { "email": "qa-{{$run}}@example.com" },
  "steps": [
    { "name": "create customer",
      "http": { "method": "POST", "path": "/customers", "json": { "name": "QA", "email": "{{email}}" } },
      "expect": { "status": 201, "json": { "/email": "{{email}}" } },
      "capture": { "customerId": "/id" } },
    { "name": "customer row exists",
      "db": { "sql": "SELECT id, email FROM customers WHERE email = '{{email}}'" },
      "expect": { "rows": 1, "row": { "id": "{{customerId}}" } } },
    { "name": "create order",
      "http": { "method": "POST", "path": "/orders", "json": { "customerId": "{{customerId}}", "item": "keyboard", "quantity": 2 } },
      "expect": { "status": 201, "json": { "/status": "created", "/quantity": 2 } },
      "capture": { "orderId": "/id" } },
    { "name": "order stored",
      "db": { "tool": "order_by_id", "params": { "id": "{{orderId}}" } },
      "expect": { "row": { "status": "created", "quantity": 2 } } },
    { "name": "orders count",
      "db": { "sql": "SELECT COUNT(*) AS total FROM orders" },
      "capture": { "total": "/0/total" } }
  ] }
```

- `http`: `method`, `path` (relative to `qa.api.url`, or an absolute URL), optional `headers`, and one of `json` or `body`. Redirects are not followed. `expect`: `status` (without it any status below 400 passes, so a forgotten status cannot hide a server error), `json` (JSON pointer to expected value, RFC 6901), `body_contains`, `headers` (name to substring).
- `db`: `{ "tool": "<tool of the tools file>", "params": {...} }` or `{ "sql": "SELECT ..." }` (run through `anvil_select`). `expect`: `rows` (count), `row` (columns the first row must have), `contains` (columns some row must have).
- `capture`: variable name to JSON pointer into the response body (HTTP) or the rows array (database, e.g. `/0/total`). A missing pointer fails the step.
- Comparison is exact JSON equality, except two numbers compare by value (SQLite returns `2`, an API may return `2.0`).
- `{{name}}` works in every string value. A string that is exactly `{{name}}` takes the variable with its JSON type (a captured count stays a number); elsewhere the value is written into the text. `{{$run}}` is unique for every scenario execution (use it for emails). An unknown variable is a step error, never an empty string. Inside `sql`, a `'` in a substituted value is doubled so it cannot end the literal around the placeholder; `tool` plus `params` is the safe form for untrusted values.
- A scenario stops at its first failing step (the later ones are reported as not run); the next scenario still runs.

**Running.** `anvil qa api [NAMES...] [--start] [--list] [--json]` runs every scenario, or the named ones (file name or `name`). `--start` runs `qa.api.start_command` in `qa.api.start_cwd` when the API does not answer at `url + ready_path`, waits up to `ready_timeout_secs`, and stops the whole process tree afterwards; without it an unreachable API is one clear error. `--list` validates the files. Exit 1 when a step fails, a file is invalid, or the API cannot be reached. A failure shows the step, what was expected and what came back (status, the offending JSON pointer with its actual value, or the first rows of a database check, truncated), and the full structured result lands in `.harness/.state/qa/api/<run-id>/report.json`.

**Tier 2.** When `qa.api.url` is set and a changed file is under `qa.api.paths` (or `anvil check --full`), `anvil check` runs the scenarios if the API answers, or starts it when `autostart` is true; otherwise it prints one advisory line. Failing scenarios fail Tier 2. A backend logic change classifies as Tier 1, so a plain `anvil check` raises the tier to Tier 2 for such changes and prints `tier raised to Tier2: qa.api.paths touched`; nothing else changes (the deps audit, visual QA, and Sonar keep their own conditions). An explicit `--tier 0` or `--tier 1` opts out, which keeps the pre-commit hook and the Stop gate fast.

## Safety Model

Anvil hooks only deny, ask, or stay silent. They never approve a tool call, so the permission system of the host stays in charge. The Security Guard inspects command text (including wrappers, nested shells, substitutions, here-documents, and PowerShell) as a safety net against accidents. It is not a sandbox: scripts on disk and dynamically built commands are outside its reach.

Tier 1 has a latency target (`tier_budgets.tier1_secs`) and a separate hard limit per process (`tier_budgets.tier1_timeout_secs`, 300 by default). Runs that hit the limit are reported as `TIMEOUT`.

## Security Guard

The guard checks every shell command (and, for MCP tools other than `mcp__anvil__*`, the `cli_command`, `command`, `cmd`, `script`, `sql`, `query`, and `statement` fields) before it runs and sorts risky ones into categories. Each category has a decision, `ask`, `deny`, or `allow`, kept in the `security_guard` section of `.harness/config.json`:

| Category | Covers | Default |
|----------|--------|---------|
| `cloud` | `aws`, `gcloud`, `gsutil`, `az` deletions (`terminate-*`, `delete-*`, `s3 rb`, `s3 rm`, `projects delete`, ...) | `deny` |
| `infra` | `terraform`/`tofu`/`terragrunt destroy`, `state rm`, `apply -auto-approve`, `pulumi`, `cdk`, `serverless`, `sam`, `helm`, `kubectl delete`/`drain` | `deny` |
| `disk` | `mkfs`, `dd` onto a device, `wipefs`, `diskpart` | `deny` |
| `containers` | `docker`/`podman` `system prune`, `volume rm`, `compose down -v`, forced bulk removal | `ask` |
| `database` | `DROP`, `TRUNCATE`, `DELETE` without `WHERE`, `ALTER TABLE ... DROP`, Mongo `dropDatabase()`, Redis `FLUSHALL` | `ask` |
| `git` | `reset --hard`, force pushes (including `--force-with-lease`), `clean -f`, `branch -D` | `ask` |
| `filesystem` | recursive deletion of the root, home, `.git`, or paths outside the repository | `ask` |
| `secrets` | reading or copying `.env`, keys, and credential files | `ask` |
| `opaque` | piped downloads, encoded or deeply nested shell code that cannot be inspected | `ask` |

Custom regexes are matched against the raw command text. Precedence is `deny_patterns`, then `allow_patterns`, then `ask_patterns`, then the category decision, and `allow` makes the guard stay silent. Anchor patterns (`^terraform destroy -target=module\.sandbox$`), because a chained command is matched as a whole. An invalid regex is ignored when the hook runs and flagged by `anvil guard list`.

```bash
anvil guard list                       # decision per category and custom patterns
anvil guard set cloud ask              # ask | deny | allow
anvil guard add deny '^kubectl apply'  # also: ask, allow; anvil guard remove <regex>
anvil guard reset                      # back to the defaults
anvil guard test "aws s3 rb s3://b"    # decision, category, and reason; runs nothing
```

The writers keep every other key of `.harness/config.json` and refresh `permissions.deny` / `permissions.ask` in `.claude/settings.json` (`anvil sync` does the same) with a fixed list of Anvil-managed `Bash(<command>:*)` rules, for example `Bash(aws ec2 terminate-instances:*)` or `Bash(terraform destroy:*)`. Rules outside that list are never touched.

The agent cannot relax its own guard: `anvil guard set|add|remove|reset` and edits of `.harness/config.json` that touch `security_guard` always ask, whatever the configuration says, and in orchestrator mode those subcommands are reserved (`guard list` and `guard test` stay readable). The guard inspects command text only, so scripts on disk and dynamically built commands escape it. Only Claude Code and Antigravity run the hook; Codex, Cursor, and Windsurf have no hooks, so there the guard does nothing.

## Orchestrator Mode

While the mode is on, Anvil hooks enforce the roles in Claude Code. The main thread inspects, verifies, and delegates, but cannot edit files or write through the shell. `anvil-executor` is the only role that writes, limited to the `SCOPE:` paths of its own latest brief, and cannot commit, manage tasks, or spawn agents. Several executors can run at once: each one's scope is read from its own Claude Code transcript, a brief whose scope overlaps a running or starting executor is refused, and `anvil check --scope <paths>` verifies one executor's files. Agents cannot turn the mode off. The orchestrator stages, commits, and pushes when the user asks (`git add`, `commit`, `push`, `switch`, `merge`, `tag`, and `gh pr create`, among others; destructive forms such as `reset --hard` or a force push still ask the user first), while executors never do and `git apply`/`git am` stay refused for the orchestrator because they write code. `anvil <command> --help` is open to every role. File tools and visible shell writes are checked: redirections and the operands of file-writing commands, with PowerShell parameter values such as `-ItemType` left out and `cd`/`Set-Location` with a literal directory applied to the commands after it. Edits under paths the repository's `.gitignore` excludes are not recorded in the active task and need no task decision at `Stop`, and `Stop` does not ask to close the in-progress task while one of the session's executors is still running. A program the executor runs can still write elsewhere, and an operand that holds an unexpanded variable (`$X`, `${X}`, `$env:X`, `%X%`) or follows a `cd` to a directory only the shell knows cannot be checked statically and is skipped, so the orchestrator reviews the diff. Reviews are mandatory and cheap: `anvil review packet` (MCP `review_packet`) prints a compact digest of a task's change (files with line and test-assertion counts, the last check result, a review checklist, and a token-capped diff), and `anvil review approve <task> "<what you verified>"` approves it. The approval is bound to the content of the task's files, `task_done` is refused until the current content is approved, any later edit needs a new review, and executors cannot approve. Executors load only the tools they need to search, edit, build, test, and read docs, plus the Anvil MCP tools, which keeps each one's starting context small; `anvil orchestrator tools` lists the MCP servers Claude Code is configured with (project, local, user, and enabled plugins) and stores the ones you pick in `orchestrator.executor_tools`; `--add` also takes servers the desktop app adds by itself. The mode is enforced in Claude Code only; other tools working in the same repository are not affected. Turning the mode off is just as explicit: the next prompt carries one `[orchestrator-mode]: OFF` notice telling the agent that earlier orchestrator instructions (including `/orchestrate`) no longer apply, and while the mode is off the main thread cannot start `anvil-executor` (other subagents stay available; executors already running may finish).

## Slop Benchmark

`crates/anvil-cli/slop_bench/` holds small changes with known slop (escape hatches, TODOs, unused new code, duplicated blocks, weakened or skipped tests) and clean changes that must stay silent. Each `.case` file lists the files before and after the change and the findings `anvil check` must report. The benchmark fails on any missed or unexpected finding, and `known-gap` entries record slop Anvil does not catch yet: when one starts being caught, the benchmark fails until the case moves to `expect`. Calibrate a new rule here before shipping it.

```sh
cargo test -p anvil-cli --test slop_bench -- --nocapture   # per-rule caught / missed / false-positive table
```
